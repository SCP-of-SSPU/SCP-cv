# 开发迭代与Git版本恢复

**Scope**: 按用户确认，当前快速迭代、没有现场维护需求。本文件取代早期复杂迁移设计，保留文件名只为不打断已有文档链接。

## 当前做法

1. 按共享前端、控制服务、媒体适配等可验证切片修改，代码/规范/锁文件纳入Git。
2. 每个切片运行相关测试后形成小提交，便于比较、定位、revert。已有未提交用户改动必须保留。
3. 新.NET后端在单独数据目录初始化，测试使用fixture；不要求从旧库导入账户、媒体或运行状态。
4. 一个功能完成替换后可在正常提交中清理旧实现，历史由Git保留，不要求长期维持新旧两套程序同时可运行。

## 明确不做

不建设专用数据搬迁工具、逆向导出、生产切流、停播窗口、双写/双轨同步、旧密码哈希兼容、文件回退隔离区、15分钟恢复指标或完整使用周期的退役门槛。新栈EF建表/schema演进仍是普通开发需要，不属于被取消的跨栈迁移工程。

## Git的边界

Git只恢复被跟踪的源码、规范与锁文件，不恢复被忽略的数据库、上传媒体、日志、凭据或运行中的Office/播放器状态。恢复旧代码后数据结构可能不匹配：提示原因并选择另一个新数据目录，不自动清库。

不因用户说“靠Git管理”而获得删除现有数据库或媒体的授权；确需清空时单独明确目标。不要用reset --hard、clean等命令处理未知用户改动。本次规划不执行任何Git提交、回退或数据操作。

## 仍须保留

命令队列恢复、失败时保留旧画面、单COM/PDF规则、协作退出和资源清理是播放器功能，不是生产版本回滚，继续按原运行时合同实现。只要测试会影响真实显示器/音响/设备，就要明确测试边界。
