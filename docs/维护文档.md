# SCP-cv 维护文档

本文面向项目维护者，记录 SCP-cv 的目录职责、配置边界、运行时资产、验证流程和现场故障处理方式。

SCP-cv 服务于上海第二工业大学 28#108 多媒体显示系统。维护时优先保证现场可运行、可回滚、可验证。

## 2. 目录职责

| 路径 | 职责 |
|------|------|
| `scp_cv/` | Django 配置、业务服务、播放器和管理命令 |
| `scp_cv/player/ppt_broker/` | PowerPoint Broker 合同、AF_PIPE 传输、单一 STA 执行器、COM 后端和 Win32 嵌入实现 |
| `frontend/` | Vue 3 + Vite 控制台 |
| `protos/` | gRPC 合同 |
| `tests/` | pytest 测试 |
| `docs/` | 使用、维护、OpenAPI 和变更记录 |
| `tools/third_party/` | MediaMTX、gRPC-Web 工具和 VLC runtime |
| `media/` | 本地上传和预览文件，运行时生成，不提交 |
| `logs/` | 运行日志根目录，`app/` 保存 Django 应用日志，`runall/<启动时间>/` 保存一次启动内的子进程日志，只提交 `.gitkeep` |

## 3. 配置来源

配置分为两层：

- 根目录 `.env`：后端、MediaMTX、gRPC、Django 和现场运行参数。
- 根目录 `config.toml`：固定启动数据，目前只包含默认管理员。
- `frontend/.env`：Vite 前端端口和后端直连地址。

维护要求：

1. 不把现场私有 `.env` 提交到版本库。
2. 修改 `.env.example`、`frontend/.env.example` 或 `config.toml` 固定数据结构后，同步更新 `README.md` 和 `docs/使用文档.md`。
3. `VITE_BACKEND_TARGET` 以 `frontend/.env` 为准；`runall` 只在前端未配置时注入兜底值。
4. 现场局域网访问必须使用浏览器可直连的后端地址，不能依赖 Vite 反向代理。

PowerPoint Broker 运行时：

- 当前 Windows 用户和 Session 只有一个 Broker，通过命名互斥量防止重复实例。
- 播放器使用 Session 专属 Windows `AF_PIPE` 调用 Broker；默认管道名包含 Windows 用户和 Session ID。
- `%LOCALAPPDATA%\SCP-cv\runtime\ppt-broker.auth` 保存 AF_PIPE 认证密钥，首次启动时独占创建。
- `%LOCALAPPDATA%\SCP-cv\runtime\ppt-broker.json` 只保存管道地址、Broker PID 和代次，不包含认证密钥。
- 上述文件是本机运行状态，不进入仓库；认证文件不得写入日志、复制到其它主机或纳入备份分发。
- Broker 内部只有一个 COM STA 和一个高低优先级队列；打开、关闭、控制和状态读取优先，应用级与文件级预热使用低优先级。
- `PowerPointComBackend` 懒加载一个 PowerPoint Application，PNG 预览导出、`.ppsx`/`.pps` 缓存导出、预热以及窗口 1-4 的 Presentation 和放映会话全部通过该 Application 执行；Django 和播放器进程不持有 COM 对象。
- Application 创建前后快照 `POWERPNT.EXE` 的 PID 与创建时间；优先取 Application HWND 所属 PID，无法读取时只接受唯一新增 PID。只有能定位到具体 Application 且 PID 不在启动前快照中时才取得所有权，启动前已有 Application 不修改全局 `DisplayAlerts`。
- 窗口化放映保持完整范围，`StartingSlide` 只作为兼容提示；`Run()` 成功后对非首页目标显式 `GotoSlide()`，不得恢复会让页码变成相对值的区间放映设置。HWND fallback 必须匹配当前独立 `Presentation.Name`；untitled 副本可能显示为“演示文稿1/2/3/4”，不能错误地要求标题包含原始源文件名。
- 生产父链为 `SlideShowWindow → Broker 原生 host → Player 视频容器`。关闭或 `View.Exit()` 前先隐藏窗口、脱离 host 与远端 Player、把 SlideShowWindow 恢复为顶层 popup，再销毁 host；兼容直接嵌入路径执行同样的顶层恢复。
- 每次公开关闭都必须释放对应 View、源 Presentation、放映 HWND 和 host；最后一个公开会话也不得转成隐藏放映守护。为规避真实 Office 在嵌入式放映数回到零后下一次 `Run()` 返回 `E_FAIL`，Broker 会在关闭最后一个源前创建一个无窗口、无 SlideShowWindow、未注册为会话的空白 Application sentinel。物理冒烟会在全部公开会话关闭后重新打开全部窗口验证该状态。
- 单窗口关闭不调用 `Application.Quit()`。Broker shutdown 处理自己的会话、sentinel 和预热资源，并仅在确认没有外部文档时退出自有 Application；`Quit()` 失败后的强制清理必须再次精确匹配 PID、创建时间、进程名且确认无顶层窗口，否则保留进程。禁止恢复播放器侧全局扫描或终止 `POWERPNT.EXE` 的兜底逻辑。
- Player 开发窗口 resize 经 50 ms 防抖后调用当前 Adapter；PPT Adapter 发出 AF_PIPE `resize`，由 Broker 按 Player 当前客户区同步 host 与放映窗口。

### 6.1 持久化控制命令

`ControlCommand` 是窗口 1-4 和背景音频的指令真值来源。每条记录包含目标、命令、参数、批次、消费者、取消标记、错误信息和开始/结束时间，状态依次为 `pending`、`executing`，最后进入 `succeeded`、`failed` 或 `cancelled`。

- 每个目标最多只有一条 `executing` 记录；消费者通过条件更新原子领取最早的 `pending` 指令。
- 同一批次保持写入顺序。终止类批次可取消尚未领取的旧指令，并把旧的执行中指令标记为待取消。
- 领取时写入随机 `consumer_id`、PID、进程创建时间和心跳；只有实际领取的 `consumer_id` 可以确认结果，若执行期间收到取消请求，最终状态强制为 `cancelled`。
- 播放器每 5 秒先续约自身执行记录，再检查负责目标上的其它消费者。默认租约为 30 秒；只有进程不存在、PID 创建时间不匹配或租约过期的 `executing` 才标记失败且不重放，仍存活并持续续约的播放器保持所有权。
- 播放器正常退出时立即把本进程未完成记录标记失败；尚未领取的 `pending` 指令继续保留。
- `PlaybackSession.pending_command/command_args` 与背景音频旧字段只镜像最早的未完成指令，用于一个稳定版本的兼容读取，不得重新作为写入或消费入口。
- 终态记录默认保留七天后由清理任务删除。迁移会把升级前非空的旧单槽指令导入队列。

## 7. 验证基线

后端变更：

```powershell
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
uv run pytest tests/ -v
```

前端变更：

```powershell
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

配置或启动流程变更：

```powershell
uv run pytest tests/test_runall_command.py -v
uv run pytest tests/test_run_player_command.py tests/test_run_ppt_broker_command.py -v
uv run pytest tests/test_ppt_broker.py tests/test_ppt_broker_transport.py -v
uv run python manage.py runall --skip-player --skip-mediamtx
uv run python manage.py runall --headless --skip-mediamtx
```

`runall` 的主要启动顺序是 MediaMTX / gRPC-Web（未跳过时）→ Django 与健康检查 → 启动状态重置 → Vue（未跳过时）→ 连接或启动 PowerPoint Broker 并等待 AF_PIPE readiness → 播放器。当前 Windows Session 已有健康 Broker 时，runall 记录其 PID + generation 后复用且不取得关闭所有权；否则启动 required 自有 Broker。监控期间 identity 变化或断开按关键进程退出处理。清理按反序先停所有播放器；自有 Broker 先由客户端 `shutdown` 并等待，复用 Broker 保持运行。Broker 绝不走递归 PowerPoint 进程树终止，避免误杀 Broker 管理的或用户已有的 `POWERPNT.EXE`。`--skip-player` 调试模式若仍要验证 PPT PNG/播放缓存导出，必须另行启动 `run_ppt_broker`。

独立 `run_player` 会通过 runtime helper 连接健康 Broker，不存在时自行启动并记录进程所有权；只有它自己启动的 Broker 才会在退出时被关闭。`--only-window` 是 runall 或父播放器的子进程模式，只允许连接已有 Broker，缺失时应明确报错，不得各自创建 COM 或 PowerPoint 实例。

### 7.1 四窗口 PPT 并发物理冒烟

`ppt_smoke` 是面向 Broker 会话隔离和 Win32 嵌入关系的侵入式诊断，不是普通自动化单元测试。它固定使用窗口 1-4，会替换 Broker 中这些窗口的现有 PPT 会话；必须在维护窗口、当前登录用户的交互桌面执行，不得与正式播放并行。

先启动 `runall` 或单独运行 `uv run python manage.py run_ppt_broker`，再选择一个至少 5 页的已登记 PPT source ID：

```powershell
uv run python manage.py ppt_smoke --windows 1,2,3,4 --source-ids 42 --iterations 3 --timeout 120
```

`--source-ids` 接受一个四窗共享 ID，或按窗口顺序给出四个 ID。命令先验证 ID、PPT 类型、可用状态和本地文件，再创建四个临时 PySide 原生宿主窗口，并在 worker 运行期间保持 GUI 消息循环。旧 `run_ppt_physical_smoke` 路径型入口继续兼容，也可显式传入四个已有容器 HWND；参数必须四项全给或全不填：

```powershell
uv run python manage.py run_ppt_physical_smoke `
  --ppt "D:\Slides\smoke.pptx" `
  --window1-hwnd 0x10101 --window2-hwnd 0x10102 `
  --window3-hwnd 0x10103 --window4-hwnd 0x10104 `
  --iterations 3 --broker-timeout 120
```

每轮从四个调用线程同时提交 OPEN；Broker 仍在唯一 STA 内串行执行 COM。测试依次验证：

1. 四个 `slideshow_hwnd` 非零且唯一，Broker 状态指向对应 Player 容器；Win32 严格验证 `SlideShow → Broker host → Player` 两级父链，兼容没有中间 host 的直接父链。
2. 窗口 1-4 分别 GOTO 第 2/3/4/5 页，并在每一步确认其它窗口页码、HWND 和父链没有变化。
3. 按轮次关闭一个窗口，确认剩余三个窗口的页码、HWND 和父链保持不变。
4. 重开被关闭窗口，再次确认四个活动 HWND 唯一、父链正确且四窗仍在各自目标页。
5. `finally` 幂等关闭本轮全部 owner 会话；任何清理错误都把该轮标记为失败。

JSON 顶层字段为 `success`、`source_ids`、`ppt_paths`、`windows`、`iterations_requested`、`iterations_completed`、`broker` 和 `rounds`。每轮包含 `iteration`、`status`、`slideshow_hwnds`、`parent_hwnds`、`navigation_slides`、`closed_window_id`、`surviving_slideshow_hwnds`、`reopened_slideshow_hwnd`、`final_slides`、`error_message` 和 `cleanup_errors`。执行型失败会先打印 JSON，再抛 `CommandError` 返回非零；前置配置错误直接以非零 `CommandError` 返回，并保留原始错误和处置提示。

该诊断没有 REST 入口。现有 `POST /api/playback/physical-smoke/` 依赖数据库播放器链路，适合逐窗口、逐媒体类型回归，但不能安全携带 Broker owner 或真实父 HWND，因此不能替代此管理命令。

## 8. 故障定位

### 8.1 前端连不上后端

1. 检查 `frontend/.env` 的 `VITE_BACKEND_TARGET`。
2. 检查 Django 是否监听对应地址和端口。
3. 浏览器访问 `${VITE_BACKEND_TARGET}/api/sessions/`。
4. 检查最新 `logs/runall/<启动时间>/django.log` 或 `logs/app/scp-cv.log`。

### 8.2 SRT 播放失败

1. 检查 MediaMTX API：`http://127.0.0.1:9997/v3/paths/list`。
2. 检查推流 URL：`srt://<主机IP>:8890?streamid=publish:<流标识>&latency=30000&pkt_size=1316`；OBS 在其它机器上时不要使用 `127.0.0.1`，本项目未开启 RTMP。
3. 检查 VLC runtime 中的 `libvlc.dll`、`libvlccore.dll` 和 SRT 插件。
4. 检查 `logs/app/scp-cv.log` 是否有 `libVLC 初始化失败` 或播放器错误详情。

### 8.3 PPT 异常

1. 确认当前 Windows 用户已安装 Microsoft PowerPoint，并能手动打开目标 PPT 文件。
2. 确认 `runall` 和播放器运行在当前登录用户的交互桌面；PowerPoint 缺失或 Broker 无法初始化 COM STA 时不会回退到其它后端。
3. 检查最新 `logs/runall/<启动时间>/powerpoint-broker.log`。播放器日志应连接同一个 Broker PID 和代次，不应再出现播放器内 COM 线程或每窗口独立 COM 实例。
4. 检查 `%LOCALAPPDATA%\SCP-cv\runtime\ppt-broker.json` 的管道地址、PID 和代次，再确认对应 PID 存活。元数据可能因异常退出而陈旧，最终以 AF_PIPE health 为准。
5. 若认证文件损坏，先停止 runall、所有播放器和 Broker，再备份并删除 `%LOCALAPPDATA%\SCP-cv\runtime\ppt-broker.auth` 后重启，让 runtime helper 重新生成；运行中不得替换密钥。
6. 多窗口 PPT 同时播放时，窗口 1-4 可以有独立 PySide 进程，但必须共享一个 Broker 和一个 PowerPoint Application。每个活动窗口应有唯一放映 HWND；其直接父 HWND 通常是 Broker host，host 的父 HWND 才是对应播放器容器。
7. 检查 Broker 日志中的窗口 ID、source ID、Broker/PowerPoint PID、放映 HWND、父 HWND、耗时和重试 HRESULT。出现多个候选 HWND 时 Broker 会明确失败，不应继续使用最大窗口等不安全回退。
8. 上传或导入 PPT 后没有缩略图或播放缓存时，同时检查 `logs/app/scp-cv.log` 与 `powerpoint-broker.log`。`PPT_PREVIEW_WORKER_TIMEOUT_SECONDS` 保留旧名称，现控制 Broker PNG 预览导出调用超时；`PPT_PLAYBACK_EXPORT_TIMEOUT_SECONDS` 控制 Broker `.ppsx`/`.pps` 缓存导出调用超时。两类导出与放映、预热共享同一个 STA/Application。
9. 若控制台长时间停留在“加载中”，同时检查 `ControlCommand` 的 `executing/failed/cancelled` 状态、consumer PID/创建时间/心跳租约和 Broker 日志。只有进程已退出、身份不匹配或租约过期的旧执行记录会失败且不重放；仍存活并持续续约的播放器保持所有权。不能只看兼容 `pending_command` 镜像。
10. 若放映窗口卡住，优先执行“应急控制 → 重置 PPT 放映”；该操作通过有序命令批次关闭并重开目标窗口，不会重启其它窗口的 PowerPoint 实例，因为实例只存在于 Broker。
11. 最后一个外部会话关闭后，应确认 Broker 会话已注销且没有残留 SlideShowWindow；Broker 自身、共享 PowerPoint Application 和无窗口 sentinel Presentation 可继续存活到 Broker shutdown。PowerPoint 可能把旧数值 HWND 复用为普通 Application frame，诊断时必须结合标题/class 判断，不得只看 `IsWindow()`。
12. 不要手工结束未知 `POWERPNT.EXE`。Broker 只关闭自己的 Presentation，并仅在确认没有外部文档时退出自有 Application；强制清理还要求 PID 与创建时间精确匹配且无顶层窗口，用户手动打开的文档必须保留。

### 8.4 后台 runall 异常

1. 使用 `uv run python manage.py runall --headless --service` 后，先查看 `logs/runall/service/runall-service-<时间>.log`。
2. 子进程启动失败时，继续查看对应启动批次下的 `logs/runall/<启动时间>/mediamtx.log`、`django.log`、`vue-前端.log`、`powerpoint-broker.log` 或 `pyside-播放器-<窗口号>.log`。
3. 通过 SSH 启动时必须使用 `--service`。直接在 SSH 会话运行 `runall --headless` 会位于 Windows Session 0，PySide 只能看到服务会话虚拟屏，无法创建 4 个物理显示窗口。
4. `--headless` 窗口未出现时，检查 Windows 显示设置中的显示器 ID 是否与 `--window1` 到 `--window4` 参数一致。
5. 未配置 `--gpu` 时属于系统默认 GPU 行为；现场需要固定显卡时显式传入 `--gpu <ID>`。
6. Broker readiness 超时或 required Broker 退出会触发 runall 反序清理；先看 `powerpoint-broker.log` 和 runtime 元数据，不要单独反复重启某个 `--only-window` 播放器。

### 8.5 设备电源无响应

1. 确认现场设备 IP 和端口未变更。
2. 确认主机到设备网段可达。
3. 检查防火墙或交换机策略。
4. 查看控制台返回的设备错误详情。

## 9. 发布维护流程

1. 确认工作区状态：`git status --short --branch`。
2. 同步基线：`git pull --rebase`。
3. 按最小影响面修改代码、配置和文档。
4. 运行对应验证命令。
5. 更新 `docs/CHANGELOG.md`。
6. 按独立可审查块提交。

提交信息格式：

```text
type(scope): 中文摘要
```

示例：

```text
fix(frontend): 修复前端环境变量优先级
docs(repo): 补充现场维护文档
```
